# パフォーマンス改善・リファクタリングの調査の型


模擬案件での学習内容を、AIの補助を使って整理した復習用メモです。
「**振る舞いを変えずに、中身だけ良くする**」タイプのチケット（パフォーマンス改善・リファクタリング）で使う調査手順のまとめ。

- **共通の流れ**：どのチケットでも使う 8 ステップ
- **パターン A：クエリ最適化（N+1）**：画面の表示が重い（例：T-B-01、T-A-01）
- **パターン B：メモリ最適化（chunk 処理）**：大量データを扱う処理がメモリを使いすぎる（例：T-B-02）


- 対象リポジトリ：[Certify-LMS](https://github.com/shiho5shiho/Certify-LMS)
- 題材：T-B-01「コーチダッシュボードの担当受講生一覧のクエリ最適化」
- [学習記録の一覧に戻る](../README.md)

本文中のファイル名・クエリ数・調査結果は、この案件での実例です。
---

## 共通の流れ

```
① 守るものを決める → ② 処理の流れを追う → ③ 問題を数字で測る
→ ④ 原因を特定する → ⑤ 既存の書き方・既存テストを探す
→ ⑥ 直す前に「壊れそうな所」を洗い出す → ⑦ 同じ物差しで測り直す
→ ⑧ 振る舞いが変わっていないことを確かめる
```

ポイントは 2 つだけ。

- **「守るもの」を最初に決める**（何を変えてはいけないか）
- **直す前と後を「同じ物差し」で測る**（数字・テスト・結果）

各ステップで「何を見るか」はパターンによって変わる。

| ステップ | パターン A：クエリ最適化（N+1） | パターン B：メモリ最適化（chunk） |
|---|---|---|
| ② 流れを追う | ルート → Controller → Action → Blade | スケジュール定義 → Command → Action / Service |
| ③ 測る物差し | **SQL の回数** | **メモリ使用量**（＋発行される SQL） |
| ④ よくある原因 | ループ内のクエリ・遅延読み込み | `get()` / `all()` で全件を一度に読み込む |
| ④ 直し方 | `with` / `withCount` / `withMax` | `chunkById` / `lazyById` / `chunk` / `cursor` |
| ⑥ 壊れそうな所 | 値の型・null・属性名・並び順 | 取りこぼし・二重処理・トランザクションの単位 |
| ⑧ 振る舞い確認 | 画面の修正前・修正後の比較 | 処理後の **DB の状態・処理件数** の比較 |

---

### ① 守るものを決める（チケットを読む）

チケットから「変えてはいけないもの」と「スコープ外」を書き出す。これが完了条件とテストの元になる。

| 確認すること | 例 |
|---|---|
| 変えてはいけない振る舞い | 表示内容・並び順・絞り込み／処理対象・処理結果・実行タイミング |
| スコープ外 | 他の画面・他の処理、キャッシュ導入など |
| ゴール | 件数が増えても重くならない／メモリを使いすぎない |

> 💡 「振る舞いは不変」と書かれたチケットでは、**仕様を良くしたくなっても触らない**。気になる点は別件としてメモする。

### ② 処理の流れを追う

**入口から順に** 追うと迷わない。入口はパターンで変わる（各パターンの節を参照）。

あわせて Model とマイグレーションも見る。

| 場所 | 見るもの |
|---|---|
| Model | リレーション定義、`SoftDeletes`、グローバルスコープ、`$casts`、Observer / イベント |
| マイグレーション | インデックスの有無 |

### ③ 問題を数字で測る

「重そう」ではなく **数字** で測る。必ず **件数を変えて 2 回** 測る（件数に比例して増えれば、それが問題）。

**最優先は、既存の計測テストを探して実行すること。**

```bash
grep -rl "DB::listen\|countQueriesFor\|QueryCount\|memory_get" tests
sail artisan test --filter=<テスト名>
```

> `grep` の使い方は末尾の「付録：grep の基本」を参照。

### ④ 原因を特定する

増え方を「1 件あたり何が増えるか」に分解し、見つけた原因と照らし合わせる。

> 💡 原因の数と実測が合わないときは、まだ見つけていない原因がある。合うまで探す。

### ⑤ 既存の書き方・既存テストを探す

提供 PJ では **新しく設計するより、既存に揃える** のが基本。

```bash
# 同じ問題を他でどう解決しているか（どこにどう書いてあるか見たいので -rn）
grep -rn "withCount\|withMax\|chunkById\|lazyById" app | head

# 対象の既存テスト（ファイル名だけ知りたいので -rl）
grep -rl "<Action名>\|<Command名>" tests
```

確認すること：

- 同じ解決方法を使っている既存コードがあるか → PR の「既存実装に揃えた」根拠になる
- 既存テストが **何を確認していて、何を確認していないか** → 足りない部分だけテストを足す

### ⑥ 直す前に「壊れそうな所」を洗い出す

**取り方・処理の仕方を変える部分** ほど、結果がズレるリスクが高い。チェック項目は各パターンの節を参照。

### ⑦ 同じ物差しで測り直す

③ と **同じコマンド・同じテスト** で測る。PR で「同じテストが FAIL → PASS」「○○MB → △△MB」と並べられる。

> 修正前の証跡を撮り忘れたら、`git switch main` で修正前に戻して撮り直せる（撮ったら作業ブランチに戻る）。

### ⑧ 振る舞いが変わっていないことを確かめる

- **自動テスト**：守るもの（①）が改修前と同じことを確認するテストが通る
- **目視・実行結果**：画面のスクショ、またはコマンドの実行結果・DB の状態を比較する

## パターン A：クエリ最適化（N+1）

**対象**：一覧画面・ダッシュボードなど、件数が増えると表示が重くなるもの
**例**：T-B-01 コーチダッシュボードの担当受講生一覧のクエリ最適化

### ② 流れを追う

```
routes/web.php → Controller → Action / Service → Model（リレーション）→ ViewModel → Blade
```

| 場所 | 見るもの |
|---|---|
| Action / Service | `get()` の後の `foreach`、ループの中のクエリ |
| Blade | `$item->relation->column` のようなリレーション参照（遅延読み込みの発生源） |

> T-B-01 では `DashboardController::index()` → `FetchCoachDashboardAction` → `assigned-students-list.blade.php` の順に追った。

### ③ 測る：SQL の回数

**A. 既存のクエリ数テストを実行する（最優先）**

**B. テストの中で数える**

```php
$count = 0;
DB::listen(function () use (&$count) { $count++; });
$this->get(route('dashboard.index'));
// $count を件数違いで比較する
```

**C. 画面で見る**：Laravel Debugbar / Telescope が入っていれば、Queries タブで回数と SQL を確認できる。

> T-B-01：既存の `DashboardQueryCountTest` で **基準 14 → 受講生 6 名追加で 32**（+18 = 6 名 × 3 回）。

### ④ よくある原因と直し方

| 原因 | よくある書き方 | 直し方 |
|---|---|---|
| リレーションの遅延読み込み | Blade で `$enrollment->user->name` | `->with(['user'])` |
| ループの中で件数を数える | `foreach` で `$x->items()->count()` | `->withCount('items')` |
| ループの中で最大・合計などを集計 | `foreach` で `$x->items()->max('col')` | `->withMax('items', 'col')` / `withSum` など |
| ネストしたリレーション | `$a->b->c->name` | `->with('b.c')` |
| 全件取得してから PHP で絞る | `->get()->filter(...)` | SQL の `where` に寄せる |
| インデックスがない | `where` / `orderBy` の列 | マイグレーションでインデックス追加 |

> T-B-01：`foreach` 内の `max('started_at')`、Blade の `->user`、`->certification` の **3 回** → 実測の「1 人 3 回」と一致したので原因確定。

### ⑥ 壊れそうな所のチェック

| チェック項目 | 見る場所 | T-B-01 の結果 |
|---|---|---|
| 値の型が変わらないか（文字列 / Carbon など） | `$casts`、Blade の使い方 | 改修前の `max()` も `withMax` も文字列。Blade で `Carbon::parse` している |
| null の扱いが変わらないか | 「記録なし」等の表示 | 記録なしは null のまま |
| 属性名が変わらないか | Blade・ViewModel の参照名 | `as last_activity_at` で名前を揃えた |
| 論理削除・グローバルスコープの扱い | Model | 改修前後で同じリレーションを使うので同じ |
| 並び順 | `orderBy` の有無 | もともと指定なし → 足さない |
| インデックス | マイグレーション | `(enrollment_id, started_at)` が既にある |

### ⑧ 振る舞い確認

- 値・null・件数が改修前と同じことを確認するテスト
- 画面の修正前・修正後のスクショ比較（表示内容・並び順・件数）

## パターン B：メモリ最適化（chunk 処理）

**対象**：定期実行のコマンド・バッチ処理など、大量のレコードを一度に扱う処理
**例**：T-B-02 大量レコードを扱う定期実行処理のメモリ最適化（chunk 処理）

### ② 流れを追う

```
スケジュール定義（routes/console.php / app/Console/Kernel.php）→ Command → Action / Service → Model
```

```bash
# 登録されている定期実行の一覧
sail artisan schedule:list

# スケジュール定義の場所を探す
grep -rn "Schedule::\|->schedule\|->command(" routes app/Console
```

| 場所 | 見るもの |
|---|---|
| スケジュール定義 | 実行タイミング（毎日・毎時など）、どのコマンドか |
| Command / Action | `get()` / `all()` で全件取得していないか、取得後の `foreach` の中で何をしているか |
| ループの中 | レコードの **更新・削除**、通知の送信、別クエリ（N+1） |
| Model | Observer / イベント（一括更新に変えると動かなくなるため） |

### ③ 測る：メモリ使用量

**A. 既存のテストを探して実行する（最優先）**

**B. 一時的にメモリを表示して、件数を変えて実行する**（ローカルだけ。コミット前に必ず消す）

```php
// Command の処理の最後に一時的に追加
$this->info('peak memory: ' . round(memory_get_peak_usage(true) / 1024 / 1024, 1) . ' MB');
```

```bash
sail artisan <コマンド名>
```

件数を増やす（例：Factory や tinker で 1,000 件 → 10,000 件）と、全件読み込みならメモリが件数に比例して増える。

**C. 発行される SQL を見る**：全件取得なら `LIMIT` のない `SELECT` が 1 回だけ発行される。`DB::listen` や Telescope で確認できる。

### ④ よくある原因と直し方

原因はほぼ「**全件を一度にメモリに読み込んでいる**」こと。

```php
// 改修前：全件を一度に読み込む
$records = Model::query()->where(...)->get();
foreach ($records as $record) { ... }
```

| 直し方 | 動き | 向いている場面 |
|---|---|---|
| `chunkById(500, fn ($rows) => ...)` | ID 順に 500 件ずつ取得して処理 | **処理中にレコードを更新・削除する**とき（基本はこれ） |
| `lazyById(500)` | `chunkById` と同じ取り方で、1 件ずつ `foreach` で回せる | 書き方を `foreach` のまま保ちたいとき |
| `chunk(500, fn ($rows) => ...)` | `OFFSET` / `LIMIT` で 500 件ずつ取得 | 読み取りだけで、条件の列を更新しないとき |
| `cursor()` | SQL は 1 回、Model を 1 件ずつ作る | 読み取りだけのとき（`with()` が使えない点に注意） |
| `query()->update([...])` | Model を読み込まずに SQL 1 回で一括更新 | 単純な一括更新（**Observer・イベントが動かない** 点に注意） |

> 💡 チケットに「chunk 処理」とあっても、既存コードで同じような処理に `chunkById` や `lazyById` を使っていれば、それに揃える。

### ⑥ 壊れそうな所のチェック

| チェック項目 | 何が起きるか | 対策 |
|---|---|---|
| **取りこぼし** | `where('status', 'pending')` で絞りながら処理中に `status` を更新すると、`chunk` のページがずれて一部が処理されない | `chunkById` / `lazyById` を使う |
| **二重処理** | 並び順が不安定だと、同じレコードが 2 回処理されることがある | ID 順で取る `chunkById` を使う |
| **処理対象が変わらないか** | 絞り込み条件を書き換えると対象が変わる | `where` は改修前と同じにする |
| **トランザクションの単位** | 改修前に全体を 1 トランザクションで囲んでいた場合、chunk ごとに分けると途中失敗時の挙動が変わる | 改修前の単位を確認し、変えるなら PM 確認 |
| **Observer・イベント** | `update()` の一括更新に変えると、Model のイベントが動かなくなる | 既存がイベントに依存していないか確認 |
| **ループ内の N+1** | chunk にしても、ループの中でリレーションを参照すると SQL が増える | chunk のクエリにも `with()` を付ける（パターン A） |
| **chunk のサイズ** | 小さすぎると SQL の回数が増え、大きすぎるとメモリ削減の効果が薄れる | 既存コードや設定の値に揃える。なければ 500〜1,000 程度 |

### ⑧ 振る舞い確認

- **chunk のサイズをまたぐ件数** でテストする（例：chunk 100 件なら 250 件作って、**全件が処理される**ことを確認）。取りこぼしはここで見つかる
- 処理対象外のレコードが **処理されていない** ことも確認する
- コマンド実行後の DB の状態・処理件数を、修正前・修正後で比較する

## PM 確認が必要かの判断（共通）

次の 3 つでふるいにかける。**どれかで答えが決まるなら PM 確認は不要** → 判断の根拠は PR の「調査・設計判断」に書く。

1. チケット・要件シートに答えが書いてあるか
2. 既存コード・既存の書き方から答えが一つに決まるか
3. 改修前と同じ挙動にすれば済むか（振る舞い不変のチケット）

PM 確認が必要になりやすいのは：

- 振る舞いを変えないと目標を達成できない（例：ページネーションの導入、表示件数の上限）
- スコープ外の手段が必要になりそう（例：キャッシュ導入、キュー化）
- **途中で失敗したときの挙動が変わる**（例：全件 1 トランザクション → chunk ごとのトランザクション）
- 改修前の挙動自体がバグっぽく、「そのまま保つか直すか」を決める必要がある

## PR への書き方テンプレ（調査・設計判断）

```markdown
**調査の足取り**
- <入口> → <Command / Action> → <Blade / 処理> の順に処理の流れを確認しました。
- <問題の内容>（例：1 件あたり N 回の SQL が追加で発行されている／全件を一度に読み込んでいる）を確認しました。
  - <原因 1>
  - <原因 2>
- 修正前に <計測方法> で、<件数> 件にすると <A> → <B>（SQL 回数 / メモリ）に増えることを確認しました。

**設計判断**
- <手法> で処理する形にしました。<既存の Action / Command> でも同じ書き方をしており、既存に揃えています。
- <代替案> は <理由> のため採用しませんでした。
- <守るもの> は改修前と同じです（理由：…）。
```

## チェックリスト

### 共通

- [ ] 守るもの（変えてはいけない振る舞い）とスコープ外を書き出した
- [ ] 入口から順に処理の流れを追った
- [ ] 件数を変えて 2 回測り、増え方を数字で把握した
- [ ] 見つけた原因で、実測の増え方を説明できた
- [ ] 既存コードの同じ解決方法を探した
- [ ] 既存テストが何を確認しているかを確認し、足りない部分だけテストを足した
- [ ] 修正前と同じ方法で測り直した
- [ ] PM 確認の要否を 3 つのふるいで判断し、不要なものは PR に根拠を書いた

### パターン A：クエリ最適化（N+1）

- [ ] 「1 件あたりの増加回数」と見つけた原因の数が一致した
- [ ] 値の型・null・属性名・論理削除・並び順・インデックスをチェックした
- [ ] 画面の修正前・修正後を比較した

### パターン B：メモリ最適化（chunk）

- [ ] ループの中でレコードを更新・削除していないか確認した（していれば `chunkById` / `lazyById`）
- [ ] 絞り込み条件・トランザクションの単位・Observer への影響を確認した
- [ ] chunk のサイズをまたぐ件数で、全件が処理されることをテストした
- [ ] 一時的に追加したメモリ計測のコードを消した

## 付録：grep の基本

`grep` は **ファイルの中から指定した文字列を探すコマンド**。

```bash
grep [オプション] "探す文字列" 探す場所
```

### よく使うオプション

| オプション | 意味 |
|---|---|
| `-r` | フォルダの中を **下の階層まで全部** 探す（recursive） |
| `-l` | 見つかった行は表示せず、**ファイル名だけ** を表示する（list） |
| `-n` | 見つかった行に **行番号** を付けて表示する（number） |

オプションは `-r -l` を `-rl` のようにまとめて書ける。

### 目的別の使い分け

| 知りたいこと | コマンド |
|---|---|
| どのファイルにあるか（ファイル名だけ） | `grep -rl` |
| どこにどう書いてあるか（行番号つきで中身も） | `grep -rn` |

```bash
grep -rn "withMax" app
# → app/UseCases/Dashboard/FetchCoachDashboardAction.php:49:            ->withMax('learningSessions as last_activity_at', 'started_at')

grep -rl "withMax" app
# → app/UseCases/Dashboard/FetchCoachDashboardAction.php
```

> ⚠️ `-l` と `-n` を一緒に付けた `grep -rln` では、`-n` は意味がない。`-l` でファイル名しか表示されないので、行番号を付ける対象がないため。

### 「または」で探す

パターンの中の `\|` は「**または**」の意味。

```bash
grep -rl "DB::listen\|countQueriesFor\|QueryCount" tests
# → DB::listen / countQueriesFor / QueryCount のどれかを含むファイルを探す
```

### 結果が多いとき

`| head` を付けると、先頭 10 行だけ表示される。

```bash
grep -rn "withCount" app/UseCases | head
```
